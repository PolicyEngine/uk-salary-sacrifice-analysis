# Investigation: Reproducing Blog Post Numbers

## Summary

The CLI tool produces **revenue estimates that match the blog**, but **distributional impacts that are ~4x larger**. This document captures hypotheses for future investigation.

## What Matches

| Metric | Blog | CLI |
|--------|------|-----|
| Revenue (spread+maintain) | £3.3bn | £3.28bn (2026) ✓ |
| Revenue (spread+cash) | £7.2bn | £7.18bn (2026) ✓ |
| Revenue (absorb+maintain) | £3.7bn | £3.67bn (2026) ✓ |
| Revenue (absorb+cash) | £7.6bn | £7.58bn (2026) ✓ |
| People above £2k cap | 3.3m | 3.4m ✓ |

## What Doesn't Match

| Metric | Blog | CLI |
|--------|------|-----|
| Total SS users | 4.9m | 4.5m |
| Decile 10 % change | -0.35% | -1.33% to -1.39% |
| Decile 10 £ change | -£431 | -£1,903 to -£1,928 |
| Decile 3 % change | -0.21% | -0.11% to -1.29% |

## Key Observations

1. **Year mismatch**: The blog says "2029-30" but revenue matches **2026** CLI output. The `calculate_distributional_impact` function defaults to `year=2026`.

2. **Revenue vs distributional paradox**: If revenue matches, total distributional impact should be similar. But CLI shows ~4x larger losses per household. This suggests the distributional calculation methodology differs.

3. **HTML data history**: Git history shows the HTML data was updated 5+ times with different values:
   - `67e95aa`: Placeholder data (-1.45% for D10)
   - `45dad76`: "Real PE data" (-0.16% for D10)
   - `d2e4abf`: "Calibrated 2029-30" (had bugs - showed positive values for take_cash)
   - `45a4180`: "Fix total income" (-0.35% for D10) - final values

4. **No reproducible script**: The HTML data was manually hardcoded, not generated by a reproducible script.

## Hypotheses

### H1: Decile Assignment Difference
The blog may have used a different decile definition (e.g., equivalised income, consumption income) than the current CLI which uses `household_income_decile`.

### H2: Income Definition Difference
The distributional calculation uses "total income" = `household_net_income` + `pension_contributions_via_salary_sacrifice`. The blog data may have used a different income concept (e.g., just net income, or equivalised income).

### H3: Weighting Difference
The blog may have computed average impact **only among affected households** in each decile, while the CLI computes average across **all households** in each decile. This could explain smaller % impacts if only ~10% of households are affected.

### H4: Dataset/Calibration Change
The Enhanced FRS salary sacrifice calibration may have changed between Nov 2025 and now. However, this wouldn't explain why revenue matches but distributional doesn't.

### H5: Spread Cost Calculation Bug
The SPREAD_COST scenario applies a haircut to ALL employees. If this is being applied incorrectly (e.g., double-counting), it could inflate distributional impacts while keeping revenue correct.

## Recommended Next Steps

1. **Check if total weighted distributional impact equals revenue** - they should match
2. **Compare decile assignments** - run with different decile variables
3. **Check affected vs all households** - maybe blog only averaged over affected
4. **Find original analysis source** - the HTML data may have come from a notebook or different tool
5. **Test with older policyengine-uk version** - try v2.59.0 exactly
